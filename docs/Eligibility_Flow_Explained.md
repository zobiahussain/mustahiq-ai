# Eligibility Flow — What Runs Where

**AI-Powered Unified Beneficiary Matching & Allocation Platform — Al-Khidmat**

This document exists to settle one question: where is the LLM used, where is XGBoost
used, what is XGBoost trained on, and what are the eligibility documents actually for.

Four different mechanisms appear in this system and they are easy to confuse. They run at
different times, do different jobs, and are owned by different people.

## 1. The Four Mechanisms at a Glance

| Mechanism | What it does | When it runs | Decides anything? |
|---|---|---|---|
| LLM extraction | Reads a criteria document and writes the rules out as structured JSON | Once, when a department uploads a document | No — a human confirms its output |
| Hard rule check | Pass/fail against a program's stated policy thresholds | Every registration | Yes — eliminates |
| XGBoost | Estimates how likely a candidate is to be confirmed on closer inspection | Every registration | No — produces a confidence score for staff |
| RAG (retrieval) | Fetches relevant passages to answer a question | On demand, when staff asks the assistant | No — informational only |

A common misreading is that RAG checks eligibility. It does not. RAG is retrieval: it
fetches text to answer questions. Eligibility is decided by deterministic rules, with
XGBoost adding a confidence estimate on top.

## 2. Why Rules and XGBoost Are Both Needed

These two are not alternatives. They do different things and neither can replace the
other.

### 2.1 Rules Are Policy

A rule such as "monthly income must be under 30,000" is not a pattern to be learned. It is
a decision Al-Khidmat made and wrote down. It is arbitrary in the precise sense that
someone chose that number, and a different department chose a different one — the
education programme may cap income at 30,000 while the health programme caps it at
40,000.

No amount of training data can tell a model what a department's policy threshold is.
Rules must be read off the document, not inferred.

### 2.2 XGBoost Is Judgment

Among the people who pass the hard rules, some are stronger candidates than others in
ways no single threshold captures. That is a fuzzy pattern across many weak signals, which
is exactly what a gradient-boosted model is good at.

The useful analogy is a job posting. "Must have a degree" is a stated rule — you read it
off the posting, you do not train a model to guess it. But ranking the two hundred
applicants who do have degrees is judgment.

Rules eliminate. The model estimates confidence on what is left.

### 2.3 And Neither of Them Allocates

Worth stating plainly, because it is a third thing again: deciding who actually receives
limited resources is done by the prioritization rubric, on verified candidates only,
using transparent weights. That is not XGBoost and not rules. See the
[End-to-End Flows](End_to_End_Flows.md) document, Use Case 6.

| Stage | Mechanism | Question it answers |
|---|---|---|
| Discovery — eliminate | Hard rules from the program | Does this person meet the stated policy? |
| Discovery — rank suggestions | XGBoost | How confident are we this is a real fit? |
| Allocation — prioritise | Transparent weighted rubric | Of verified candidates, who needs it most? |

## 3. What XGBoost Is Actually Trained On

This is the question the team will ask first, and it deserves a straight answer.

### 3.1 The Honest Position for the Hackathon

Al-Khidmat is not providing real data, so there is no history of past decisions to learn
from. The model is therefore trained on synthetic data generated by the team, and the
team should say so plainly rather than implying otherwise.

A model trained on synthetic labels only learns whatever pattern was used to generate
those labels. It demonstrates that the pipeline works end to end; it does not demonstrate
predictive skill on real beneficiaries. Presenting it as more than that would not survive
a knowledgeable judge's question.

To make the demonstration meaningful rather than circular, the synthetic labels should be
generated with deliberate noise and with interactions that no single rule captures —
otherwise the model is simply relearning the rule that produced the data.

### 3.2 Where the Real Training Labels Come From Later

The design has a genuinely strong answer for production, and it is worth putting in the
pitch.

Every verification outcome is a training label. When staff contacts someone the system
flagged and records whether the need was confirmed, that record is exactly the ground
truth the model needs: the system predicted this person was a likely fit, and outreach
either confirmed it or did not.

So the target variable is: given a profile that passed the hard rules, will verification
return `'verified'`? Every row in the `verifications` table is a labelled example. The
platform generates its own training data as it operates — the more it is used, the better
its discovery gets.

This is a strong point to make in the presentation. Most hackathon ML has no path from
synthetic to real data. This one has a mechanism built into the normal operation of the
product.

### 3.3 Features

- **Profile fields:** income, household size, dependents, school-age children, education
  level, disability flag, employment status, prior assistance count.
- **Derived features:** income per household member, ratio of dependents to earners,
  distance from the programme's stated thresholds.
- **Soft signals** extracted from the criteria document — see section 4.
- **Never used as a feature:** `entry_path`, or anything describing how the person was
  found. This is enforced at the allocation stage too and applies equally here.

## 4. What the Eligibility Documents Are For

Programs do not always have clean, structured criteria. Some will only have their rules
written out in prose — a Word document saying assistance is intended for low-income
households with school-going children. Those documents serve two entirely separate
purposes.

### 4.1 Purpose One — Source of the Rules (LLM extraction, once)

1. A department admin uploads the criteria document for their program.
2. An LLM reads it once and drafts structured rules as JSON.
3. The department admin reviews the draft and confirms or corrects it. A human validates
   the AI's reading a single time, rather than the system trusting it on every one of five
   hundred registrations.
4. The confirmed rules are stored in `programs.criteria_structured`.
5. From that point on, the document is not consulted during scoring. Scoring reads the
   JSON.

Target structure for the extraction:

```json
{
  "hard_rules": [
    {"field": "monthly_income",  "op": "<=", "value": 30000},
    {"field": "dependents",      "op": ">=", "value": 1},
    {"field": "district",        "op": "in", "value": ["Lahore"]}
  ],
  "soft_signals": ["single earner household", "recent medical expense"],
  "required_documents": ["CNIC", "income proof"],
  "source_chunk_ids": ["uuid-of-the-chunk-this-came-from"]
}
```

| Part | Used by | Purpose |
|---|---|---|
| `hard_rules` | Deterministic rule check | Pass/fail. Fail one and the person is excluded. No model involved. |
| `soft_signals` | XGBoost | Become features. Raise or lower confidence without disqualifying anyone. |
| `required_documents` | The assistant, and staff | Answering what paperwork a beneficiary needs to bring. |
| `source_chunk_ids` | Explanation | Traceability — shows staff the actual sentence a rule came from. |

### 4.2 Purpose Two — Source for the Assistant (RAG, on demand)

The same document is also chunked and embedded into `program_criteria`. This is genuine
retrieval and it runs at question time, not at scoring time.

When a staff member asks the assistant something — what documents does this programme
need, or why did this person match — the relevant passage is retrieved and the answer is
generated from it, citing the source. Nothing about eligibility is decided here.

## 5. The Eligibility Flow, Step by Step

### 5.1 Setup, done once per program

1. Department admin uploads the criteria document.
2. LLM drafts structured rules. Admin confirms them. Stored in `criteria_structured`.
3. The same document is chunked and embedded into `program_criteria` for the assistant.

This happens once. It does not repeat per beneficiary.

### 5.2 Runtime, every time someone registers

1. An area manager enters the person's profile in conversation.
2. An LLM parses their free-text situation description into structured fields. The
   manager confirms the extraction. This is the only LLM call in the registration path,
   and it touches data entry, not eligibility.
3. For each active program, the hard rules are checked against the profile's columns.
   Pure Python comparison. Anyone failing a hard rule is excluded from that program
   immediately.
4. For programs that pass, XGBoost produces a confidence score using profile features
   plus that program's soft signals.
5. A `match_records` row is written per qualifying program, with the score, a
   plain-language reason, and the `source_chunk_id` the rule came from.

Total time: milliseconds. No retrieval, no LLM call, no external API in this loop.

This matters beyond speed. Because scoring is deterministic, the same person always
produces the same result. An eligibility decision that varied between runs could not be
audited or defended — which is why the LLM is deliberately kept out of this path.

### 5.3 On demand, whenever staff asks

1. Staff asks the assistant a question.
2. The question is embedded, relevant passages are retrieved from `program_criteria`, and
   the answer is generated from them with a citation.

This is the only place RAG runs in the eligibility flow.

## 6. Summary Table — Who Owns What

| Component | Mechanism | Runs when | Owner |
|---|---|---|---|
| Criteria rule extraction | LLM, one-off | Document upload | Marketplace / RAG owner |
| Criteria chunking + embedding | Embedding model | Document upload | Marketplace / RAG owner |
| Free-text profile parsing | LLM (JSON mode) | Registration | NLP role |
| Hard rule evaluation | Plain Python | Registration | Discovery engine owner |
| Confidence scoring | XGBoost | Registration | Discovery engine owner |
| Synthetic training data | Generated dataset | Before the demo | Data engineering |
| Assistant answers | RAG retrieval + LLM | On demand | Assistant owner |
| Need prioritization | Weighted rubric | Bi-weekly cycle | Discovery engine owner |

## 7. Three Things to Get Right

1. **Do not put an LLM in the scoring loop.** It makes eligibility slow, rate-limited, and
   non-deterministic, and a non-deterministic eligibility decision cannot be audited.
2. **Do not claim XGBoost is trained on real data.** It is trained on synthetic data for
   this build. The credible claim is that verification outcomes become real training
   labels as the platform operates.
3. **Do not let the LLM's extracted rules go straight into production without a human
   confirming them.** A misread threshold silently excludes people who should qualify,
   and nothing downstream would reveal it.
